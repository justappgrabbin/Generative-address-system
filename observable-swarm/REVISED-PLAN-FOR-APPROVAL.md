# Semantic SpaceTime Swarm — revised proposal

Status: proposed, awaiting your approval. No implementation or GitHub publication is authorized by this document.

## Purpose

Create the primary conditions of a persistent, moving semantic substrate. Its constituents form relationships, learn reusable transformations, and stabilize into neural networks and meshes. Those structures must perform computation and constitute the observable world. The installed application supplies an observable window and operating-system contact for that substrate.

The previous prototype is an experiment, not the completed architecture. Its proximity-based bonds, fixed particle budget, limited predictor, provisional sentences, and surfaces do not establish this mechanism. Existing code will be retained only where it passes the source and behavior checks below.

## Requirements that govern the rebuild

1. One substrate, five dimensions, and a variable number of recursively nested qualitative layers. A dimension is not a layer or a zoom level.
2. Personality and Design each express their four-dimensional organization and meet in the fifth-dimensional expression, following your correction. The older source pairings remain reference relationships, not exclusions of the other dimensions.
3. Motion and interaction continue through cycles. Local dimensional rules govern their orientation and transformations. Exact letter-to-direction assignments must be sourced before being activated.
4. Addresses retain identity, dimensional frame, position, relationships, and event history. They may change with context. A hash can index data but cannot replace semantic addressing.
5. Potential, realized expression, and trajectory change remain different records. The leading dimension is identified from the realized event. Preserve six potentials and the two action-capable possibilities without inventing which two are selected.
6. Stable learned relationships can form neural networks and meshes. They retain their constituents and perform operations through their connections. Configuration and history affect reinforcement, decay, disruption, and recovery.
7. Microstructure and macro expression remain the same evolving state. Zoom exposes constituents and relations of the visible thing. Composition can produce language, music, shapes, scenes, and other forms without requiring every composition to be a paragraph.
8. The 16-tool collection provides operational references to be audited against its documents. A tool registry entry is not evidence that the swarm has learned or embodied that operation.
9. The primary product runs in a Linux container or Linux virtual computer, with access to the files and OS capabilities exposed by that environment, offline persistence, CPU execution, and no Web Worker or GPU requirement. Provide a headless runtime and an observable interface to the same persistent substrate. JavaScript, Python, and Rust roles remain adaptable until their scale relationship is resolved.

## Proposed implementation sequence

### 1. Make the starting conditions explicit

Deliver a source-linked rule ledger. Each entry includes the original term or symbol, source/page/diagram, dimensional frame, permitted relations, transformation conditions, and what observation would confirm its application. Keep alternatives and unresolved correspondences visible.

Represent the five dimensions' qualitative structures separately. Preserve the Black Book's different macro/micro chains and the difference between a defined factor and the expression it produces. Preserve meaningful capitalization without treating uppercase characters as the sole representation of a governing primitive.

Audit the existing 16 entries against original papers and Hover 5.8 where needed. Some current entries are lite/canonical versions of the same tool; some are modern extensions. Establish exactly what each contributes before treating the list as 16 independent historical mechanisms.

Deliverable: reviewable primary-condition specification, reference examples, and a list of unresolved rules. No fabricated mappings hidden in defaults.

### 2. Build the smallest executable substrate

Implement constituents, directed typed relations, offer/accept conditions, contextual addressing, local state changes, and causal event records. Establish the smallest explicitly documented interpreter and OS input/output boundary necessary to run those rules.

Represent Boolean configurations, change contexts, grammatical composition, and ATO transformations within this substrate. Keep the 64 change contexts distinct from the 384 possible single-line transitions. Do not assume that the former automatically supply all 64 operational meanings you intend.

Use reproducible runs and event replay to inspect movement, local cycles, cross-dimensional encounters, and the event-dependent leading dimension. A display projection must not become the underlying addressing rule.

Deliverable: an inspector showing why a connection or transition occurred, which rule enabled it, and which dimensional context applied.

### 3. Establish learning and persistent collective computation

Adapt AutoLing's proposal/testing/revision mechanisms and DISEMINER's dependency composition to the relational substrate. Preserve positive examples, rejected examples, ambiguity, and correction history. Establish what supplies feedback for each task: observed consequences, explicit examples, user judgment, or a model comparison.

Train and test relations through repeated interaction. Let compatible configurations stabilize into executable networks and larger meshes. Preserve constituent identity and expose the behavior offered by the collective. Define reinforcement and decay as explicit experimental mechanisms until source-derived parameters exist.

First proof: a learned configuration must perform a small transformation on an unseen input through its connections. Inspect the execution path. Disrupt the participating connections, observe the loss of behavior, and test recovery through use. A cluster name that dispatches to a finished external function does not pass this proof.

Deliverable: inspectable learned computation, persistence across restart, and measured responses to use, disuse, and disruption.

### 4. Establish cross-modal expression and reconstruction

Ingest a small image and an associated sound/text example into addressed constituents. Separate reversible character/byte representations from learned semantic associations. ASCII, Unicode, transliteration, phonetic naming, and hashes serve different purposes.

Preserve the relationship between source data, learned features, composition, and generated output. Test reconstruction and transformation separately. The same state must support an overview of the form and a close view of its active constituents; no separate picture is substituted to simulate emergence.

Introduce temporal examples so motion is represented by persistent evolving relations, not independent unconnected frames. Measure fidelity, continuity, and CPU cost. Sound/shape/color ordering and BANTU transformations enter only through rules whose dimensional context has been established.

Deliverable: an observable form built from the substrate, continuous semantic zoom, and one documented cross-modal transformation.

### 5. Extend to scenes, people, and reusable applications

Compose proven structures into more complex forms. Add contextual Human Design chart inputs and channel relationships while preserving all five chart configurations as distinct references. Do not collapse them into a single chart or invent missing ephemeris/frame choices.

Require a recognizable, continuously moving small scene whose visible entities can be traced to their constituents. Then test reuse of learned compositions in a second task or scene, with no bespoke implementation of that task's entire operation.

Add applications, games, sites, and file execution through the same compositional mechanisms. OS contact still requires explicit compatible execution semantics: addressing arbitrary bytes does not itself define how every file format executes. Preserve unfamiliar inputs for analysis rather than silently claiming execution support.

Deliverable: evidence of generalization to a new composition, followed by a reproducible Linux container image and instructions for running it in a Linux virtual computer. Store persistent state in an explicit mounted data directory. Universal arbitrary-file execution and photorealistic world generation remain goals to demonstrate, not capabilities inferred from the word swarm.

## Acceptance evidence

- Dimensional structure: all five dimensions survive inspection; layers vary by their qualitative organization; changing zoom does not change dimension identity.
- Causality: every observed transition has reproducible inputs, context, and an execution trace. Leadership is recorded after the event.
- Learning: a held-out example succeeds using a learned configuration; counterexamples can revise it.
- Collective function: removing relevant bindings changes the operation, and restoring/relearning them can restore it.
- Persistence: saved relations, learned parameters, histories, and collective identity survive restart.
- Representation: identity persists across supported encodings; lossy transformations are identified and tested as such.
- Scene integrity: macro output and micro relations refer to the same state. Reconstruction error and temporal continuity are measured.
- Runtime: verify offline Linux operation, CPU responsiveness, persistence across container restart/replacement, and the absence of Web Workers/GPU dependence in the target environment. Document exposed files, installed interpreters, resource limits, and how to connect the observable interface.

## Decisions and unresolved derivations

- Deployment target confirmed by you: a Linux container or virtual computer. Container access is to its exposed environment; access to the surrounding host requires an explicit mount or integration. Final CPU/memory sizing will follow measurements of the first working substrate.
- Exact BANTU/letter/direction rules, the six-potential action-selection rule, and the full dimensional address transformations need an explicit derivation from the sources before activation. These are research outputs, not requests for you to re-explain the entire system.
- Exact five chart configurations, astronomical frames, and calculation settings need confirmation against existing chart code or source data before implementing calculation. Existing verified charts can remain reference fixtures during that review.
- The roles of Rust, Python, and JavaScript should be decided from the substrate's execution needs; no scale-to-language assignment is assumed.

## Approval boundary

Approval of this proposal authorizes the staged implementation above, beginning with the source-linked primary-condition ledger and executable substrate. Until then, retain the existing prototype and unpublished changes without further implementation or publication. The first implementation demonstration must show working collective computation before expanding the interface or claiming general generation.
